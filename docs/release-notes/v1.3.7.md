# v1.3.7

## The important one

**You are no longer signed out because a refresh lost a race.**

The account service rejects a refresh token it believes was already spent, which is
what happens when two processes refresh at the same moment — and by then the winner
has already written a working token to disk. The client read that rejection as "this
user is signed out", deleted the session file, and returned 401 for every request. The
result was an app that said you were signed in and did nothing when you pressed
anything, with no way back except signing in again.

It now recognises that specific rejection, keeps the session, and answers "could not
confirm right now" instead of "not signed in". A genuine rejection — revoked token,
unknown device — is still reported as invalid, but nothing is deleted behind your back.
Signing out is something you do, not something a failed refresh does to you.

## Reliable writes

**A file write is now all-or-nothing.** It used to truncate the file and then write the
new bytes, so a crash or a kill in between left a partial file with the original
already gone. Writes now go to a temporary file that is flushed and then renamed over
the target — readers see the old version or the new one, never half of each. A failed
write leaves the original untouched and no temp file behind.

## Skills, actually

**Asking for a skill now opens it.** With the index listing only names and one-line
descriptions, a Chinese request naming a skill by name went to `ask_user` and never
looked at the skill — three separate attempts, same result.
Nothing in the prompt said this was a step to take, so it did not take it.

There is now a hard rule: when you name a skill, the agent finds the tool, looks up the
exact name, and reads the skill before acting. Verified against a live model — the
request above now calls `tool_search` and `skill_view`.

## Fixes

- **The goal bar's output is no longer printed twice** when a run has finished.
- **A plan no longer marks every step complete when the run ends** on the front end
  either, matching what the server already did — an interrupted run shows the steps
  that actually finished.
- **Dates are validated before use.** `2026-02-30` and month `13` are rejected instead of
  being silently rolled forward by the date parser, and out-of-range times are refused.
- **The goal runtime rebuilds its runner when the account changes**, so a goal picked up
  after switching accounts does not run as the previous one.

## Not in this release

**Persistent goals remain off** (`VITE_GOALS` unset). The bar exists and is tested, but
its execution path has not been driven end to end against a live model in a packaged
build. Turning it on is a decision for when that has happened, not a default.

**Known, not fixed:** a process killed during a write can still lose the write itself
(the old content survives, the new content never lands). Recovering a half-finished
edit needs a journal, which is not in this change.
