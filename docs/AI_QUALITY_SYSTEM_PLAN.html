二、AI 浏览器画面（技术达成）

要实现 Grok/GPT 那种"小窗实时显示 AI 在开的网页"，需要引入 Playwright 隐形式浏览器（后台 Chromium），替换当前"控制整个真桌面"的 computer-use 场景，提供可控、可展示的隔离浏览器。

三种画面流的实现原则

方案原理延迟成本选型
周期截图 + WebSocket 推送每 ~1s 对浏览器截图 base64 → 前端替换 img~1s低✅ 首选（实现快、够用）
CDP 帧流 / WebRTC实时像素流<200ms高、复杂阶段 3 再考虑

后端新增模块

services/ai-browser.ts
  - 启动 Playwright Chromium（headless）
  - open(url) / screenshot() / click(x,y) / type() / scroll()
  - setInterval → 截图 →  emit /ws/ai-browser (base64)
  - 供 AI 工具: ai_browser_navigate / ai_browser_screenshot / ai_browser_click
  - 供质检: screenshot({widths:[375,768,1280]}) 各尺寸界面审查

前端：对话右侧固定 <AI-Browser 组件>，订阅 WebSocket 收帧；AI 操作时右上角显示当前 URL + 操作命令日志（上图 console-dark 那块），用户看着 AI 一步步操作。

三、分层审查（质检体系）达成

执行 AI 交付→ L1 机器：跑 lint/test/curl/截图→ L2 质检 Agent（拿证据核对需求）→ 执行 AI 商议修复→ 复检全绿→ （主观争议才）L3 多 AI 群聊→ 交付验收
  • L1：现有 shell_exec 跑固定命令（npm run lint / vitest / curl / 截图），产出结构化"机器报告"——确定性、零 AI 发散。
  • L2：一个带质检人设的 Agent（复用 runAgentLoop），消费 L1 报告 + 需求清单，输出带证据问题清单。
  • L3：仅当"机器判不了 + 单 AI 拿不准"的主观争议，才开多 AI 群聊民主评议（复用群聊共识引擎）。

收敛机制（防发散四件套）

机制规则
证据门禁质检意见必须带证据（文件行号/复现/curl输出），无凭证不采纳
最大轮数执行↔质检碰撞最多 3 轮，超限强制收敛（取当前最优）
分歧升级僵持交仲裁（关键问题才用多 AI / 或问人类）
达标线全维度 ≥85 且无 P0 即交付，不死磕 100

六、当前最该先做的两件事

1P0 对话地基

消息加 actor + 前端渲染多身份。这是所有后续的交互基础，改动小、风险低、立刻可见"多 AI 同流对话"。

2引入 Playwright

装 playwright，起一个隐形式浏览器，打通"AI 打开网页 → 截图 → 前端小窗展示"的最小链路。这是"AI 浏览器画面"的关键开关。

落地顺序建议：P0 → P1 质检 MVP → P2 浏览器 → P3 视觉 → P4 全自动。每一步都可单独验收、不影响现有功能。
